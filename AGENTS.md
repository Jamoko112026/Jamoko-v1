# JaMoKo Developer Guide

## Rolle
Du arbeitest als unterstützender Entwickler für JaMoKo.

JaMoKo ist eine ruhige, klare Website für lokale Betriebe, Handwerker und Dienstleister.

## Grundprinzip
Nicht lauter machen. Klarer machen.

Jede Änderung soll:
- verständlicher werden
- ruhiger wirken
- schneller laden
- Vertrauen stärken
- Kontaktaufnahme erleichtern

## Entscheidungsregel
Wenn mehrere Lösungen technisch möglich sind, bevorzuge diejenige, die:

1. für den Besucher einfacher verständlich ist,
2. langfristig wartbar bleibt,
3. Vertrauen stärkt,
4. Performance nicht verschlechtert,
5. zur ruhigen Markenidentität von JaMoKo passt.

Nicht die technisch cleverste Lösung gewinnt,
sondern die verständlichste.

## Sprache
- Deutsch
- einfach
- klar
- keine Agentur-Floskeln
- keine Übertreibungen
- keine Buzzwords

Bevorzugt:
- ruhig
- persönlich
- verständlich
- lokal
- ehrlich

Vermeiden:
- skalierbar
- revolutionär
- disruptiv
- 360° Lösung
- maximale Performance ohne Kontext

## Design
Bestehendes Design beibehalten.

Farben:
- Deep Navy #001821
- Gold #E5C58B
- Teal Green #1AC7A4

Stil:
- ruhig
- hochwertig
- klar
- organisch
- nicht überladen

Keine unnötigen Animationen.
Keine grellen Effekte.
Keine kompletten Redesigns ohne Auftrag.

## Code-Regeln
- Next.js App Router verwenden
- TypeScript beibehalten
- Tailwind-Konzept beibehalten
- bestehende Komponenten wiederverwenden
- keine neuen Libraries ohne Grund
- semantisches HTML verwenden
- Barrierefreiheit beachten

## SEO-Regeln
Jede Seite braucht:
- eindeutigen Meta Title
- eindeutige Meta Description
- genau eine H1
- logische H2-Struktur
- interne Links
- sinnvolle Alt-Texte
- saubere Canonical-URL

## Conversion-Regeln
Jede wichtige Seite soll beantworten:
1. Was ist das Angebot?
2. Für wen ist es?
3. Warum ist es vertrauenswürdig?
4. Was ist der nächste Schritt?

Primärer CTA:
- Kontakt aufnehmen
- Kostenloses Erstgespräch
- Website anfragen

## JaMoKo-Leitsatz
Erst Mensch, dann Marke, dann Mechanik.

## Arbeitsweise
Bei jeder Änderung:
1. Nur den beauftragten Bereich ändern.
2. Bestehendes Design respektieren.
3. Kleine, saubere Commits bevorzugen.
4. Keine unnötigen Umbenennungen.
5. Keine Struktur zerstören.
6. Nach Änderung prüfen:
   - npm run lint
   - npm run build
